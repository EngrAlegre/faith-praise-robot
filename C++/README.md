# C++ Lab

An interactive C++20 course: a dashboard, 46 compact
lessons across four tracks, real quizzes, and a code workspace that compiles and runs
what you type with a real compiler.

Everything is local. No accounts, no cloud, no telemetry.

---

## Start it

```bash
cd C++/          # this folder
python server.py
```

Then open **http://127.0.0.1:8765**.

`python` must be 3.9 or newer. On this machine use the full path:

```bash
"C:/Users/isaac/AppData/Local/Programs/Python/Python312/python.exe" server.py
```

Options:

```bash
python server.py --port 9000          # different port
python server.py --host 0.0.0.0       # reachable from a tablet on the same wifi
```

For a tablet, use `--host 0.0.0.0` and open `http://<this-pc-ip>:8765` on the device.
Only do that on a network you trust — see **Security** below.

## What is in the course

| Track | Lessons | Covers |
|---|---|---|
| Beginner | 14 | `main`, output, variables, types, input, arithmetic, `if`, loops, functions, strings, debugging, a score-tracker project |
| Intermediate | 12 | arrays, vectors, references, pointers, structs, classes, encapsulation, `map`/`set`, algorithms, files, headers, a fleet-status project |
| Advanced | 12 | scope and lifetime, `new`/`delete`, RAII, `unique_ptr`, `shared_ptr`, exceptions, `std::optional`, templates, lambdas, move semantics, an inventory project |
| Expert Track | 8 | concepts, ranges/views, threads and mutexes, `async`/`future`, measuring performance, build checks, a two-part capstone with a test harness |

Every lesson has the same six parts:

1. **Goal** — one sentence.
2. **The idea** — two short plain-English paragraphs.
3. **A complete program** — runnable, with its exact output and notes on the important lines.
4. **Predict before you run** — one question you answer before seeing the explanation.
5. **Quiz** — 3–5 questions with instant feedback, retries, and an explanation for every answer.
6. **Your turn** — a coding task with starter code, expected output, progressive hints,
   and a worked solution that stays hidden until asked for. Plus a common mistake and a recap.

The worked solutions are *verified by running them* (see **Verification**), so the expected
output in a lesson is what the program actually prints, not what it was meant to print.

## How progress is stored

In `localStorage`, under one key per profile:

```
cpplab.v1.faith    cpplab.v1.praise    cpplab.v1.active
```

Each profile keeps its own `completed` lessons, `quiz` best scores, and `drafts` of the
code editor. Switching profile swaps the whole store, so the two children never see or
overwrite each other's work.

- Progress stays **in that browser on that device**. Chrome on the PC and Safari on a
  tablet are two separate stores; clearing site data erases it.
- A lesson is marked complete when the learner presses the button, or automatically when
  their activity output matches the expected output exactly.
- Drafts save about half a second after you stop typing.

## How code execution works

`POST /api/run` with `{"code": "...", "stdin": "..."}`:

1. The program is written to a fresh temporary folder as `main.cpp`.
2. It is compiled with
   `g++ -std=c++20 -O1 -Wall -Wextra -static-libstdc++ -static-libgcc`.
3. If compilation fails, the compiler's message is returned and **nothing runs**.
   Paths are stripped so the message reads `main.cpp:2:27: error: ...`.
4. If it compiles, the program runs with the supplied stdin and these limits:

| Limit | Value |
|---|---|
| Compile time | 20 s |
| Run time | 5 s (then the process is killed) |
| Memory | 512 MB (Windows job object) |
| Output | 20 000 characters, then truncated and marked |
| Source size | 64 KB |

The compiler is found in this order: `CPP_LAB_GXX` environment variable → anything under
`C++/tools/**/g++.exe` → `g++.exe` on `PATH`. If none is found the Run button says so
plainly instead of pretending to run anything.

The app never claims a pass it did not measure: the verdict compares your actual stdout
with the lesson's expected output, after normalising line endings and trailing spaces.

### Security — read this before exposing it

This runner is a **local single-user tool, not a sandbox**. It stops runaway loops, output
floods and runaway memory, but learner code can still read and write files that the
Windows user can, and can open network connections.

- Binding to `127.0.0.1` (the default) is safe: only this machine can reach it.
- Binding to `0.0.0.0` for a tablet is reasonable on a home network you control, for a
  short lesson. Stop the server afterwards.
- Do **not** put this on the open internet. If you ever need that, run the runner inside a
  container or a VM with no network and a read-only filesystem.

## Add or edit a lesson

Lessons live in `content/<level>.py` as Python dicts — triple-quoted strings keep the C++
readable, and the JSON is generated:

```bash
python tools/build_course.py     # validates + writes data/*.json
python tools/verify_lessons.py   # compiles and runs everything
```

A lesson needs these keys:

```python
{
 "id": "b15", "level": "beginner", "title": "...", "minutes": 12,
 "tags": ["loops"],
 "goal": "...",
 "explain": ["paragraph one", "paragraph two"],
 "example": {"title": "x.cpp", "code": r"""...""", "output": "...", "notes": [["line", "why"]]},
 "predict": {"q": "...", "options": ["a", "b", "c"], "answer": 1, "why": "..."},
 "quiz": [{"q": "...", "options": ["a", "b", "c"], "answer": 0, "why": "..."}],
 "activity": {"goal": "...", "starter": r"""...""", "expected": "...",
              "hints": ["...", "..."], "solution": r"""..."""},
 "mistake": "...", "recap": "..."
}
```

`build_course.py` refuses to build if a lesson is missing a field, has fewer than 3 or more
than 5 quiz questions, has an out-of-range answer index, has no hints, or whose example is
not a complete program. Add `"stdin": "..."` to an example or activity when it reads input.

No app changes are needed: the nav, dashboard, search and progress all read `course.json`.

## Accounts (Firebase)

Anyone can make their own account — there are no built-in users, and no learner name appears in
the lessons. **The app opens on a sign-in screen**: nothing is shown, and no progress exists,
until someone signs in. The account name is what the app greets, in the header, in the page
title, and on the dashboard.

There is one escape hatch for a bad connection: *"Continue without an account"* opens the
course in a session that lives in memory only — reload and it is gone, nothing is saved.

| Piece | Value |
|---|---|
| Firebase project | `cpp-lab-faith-praise` ("CPP Lab", free Spark plan) |
| Auth | Email/password. A bare name is accepted: `ana` becomes `ana@cpplab.local` |
| Progress store | Firestore `users/{uid}` — one document per learner |
| Rules | `firestore.rules`: you can read and write only your own document |
| SDK | vendored in `web/vendor/` (no CDN needed at run time) |

### One-time setup in the console

Creating that provisioning through the API needs a billing account, so it is a two-click
job in the console (both free, no card):

1. <https://console.firebase.google.com/project/cpp-lab-faith-praise/authentication>
   → **Get started** → **Email/Password** → **Enable** → **Save**.
2. <https://console.firebase.google.com/project/cpp-lab-faith-praise/firestore>
   → the database already exists (`default`, asia-southeast1); opening the page creates
   the default rules release.

Then publish the rules and try a sign-up:

```bash
python tools/deploy_rules.py          # publishes firestore.rules
```

Until Email/Password is enabled the dialog says so plainly instead of failing silently.

**Rules binding (open item).** The database was created through the Cloud API, so Firebase
has no rules binding for it yet: uploads via `tools/deploy_rules.py` publish the ruleset to
the project, but the live database still evaluates the locked default and returns
`PERMISSION_DENIED`. The rules themselves are correct — the Rules simulator returns ALLOW for
an owner reading their own document. Fixing the binding is one console action: open
<https://console.firebase.google.com/project/cpp-lab-faith-praise/firestore/rules> and press
**Publish**. Until then the header shows *offline — kept here* and progress stays local.

### Where progress lives

- Signed in: `localStorage` mirror **and** Firestore, written ~0.7 s after any change.
  On sign-in the local copy and the cloud copy are merged — lessons completed on either
  side are kept, and the better quiz score wins.
- Signed out: **nothing is stored**. The gate is shown, and the offline session keeps progress
  in memory only.
- Offline: the app keeps working; writes queue and replay when the connection returns.

## Deploy to Vercel (a real public link)

The folder is ready to deploy as-is:

| Part | What it is |
|---|---|
| `web/` | the whole site — HTML, CSS, JS, vendored Firebase SDK, `web/data/*.json` |
| `api/run.py` | serverless function: compiles a program through wandbox.org and returns the same JSON the local runner does |
| `api/health.py` | reports the online compiler |
| `vercel.json` | publishes `web/` and runs `api/*.py` with a 60 s limit |

1. Push this folder to GitHub.
2. In Vercel: **Add New → Project → import the repo**.
3. Set **Root Directory** to `C++`, framework preset **Other**, no build command.
4. Deploy.

If the function is missing or fails, the browser falls back to calling `wandbox.org`
directly — the Run button stays real either way, never a fake pass.

`python tools/build_course.py` refreshes both `data/` and `web/data/`, so commit after
editing lessons.

**Privacy note:** on the hosted build, learner code is compiled by a third-party service
(wandbox.org). Locally it never leaves the machine.

## Verification

Run from this folder.

```bash
# 1. every example compiles and prints exactly what the lesson claims,
#    every starter compiles, every solution produces its expected output
python tools/verify_lessons.py

# 2. server, static files, data integrity, the runner's limits, path traversal
python tests/test_api.py
```

Current results on this machine (g++ 16.2.0, Windows 11):

```
checked 46 lessons, 0 failure(s)
21 passed, 0 failed
```

`verify_lessons.py` uses the same `runner.py` the app uses, so a lesson that passes there
behaves identically in the browser. It takes about three minutes because it compiles 138
programs (example + starter + solution per lesson).

Also checked by hand in the browser: dashboard, lesson pages, quiz scoring and retries,
profile isolation after reload, a failing compile, an infinite loop, and the layout at
820×1180 and 1180×820 (no sideways scrolling).

## Limitations

- **Cloud sync is not live yet.** Sign-up, sign-in and per-account local progress all work
  and are verified. Writing to Firestore returns `PERMISSION_DENIED` because the database has
  no Firebase rules binding (it was created through the Cloud API); pressing **Publish** once
  on the console Rules page fixes it. The app reports this honestly instead of pretending.
- **No sandbox.** See above.
- **Windows-first.** The runner uses a Windows job object for the memory cap; on macOS or
  Linux it still compiles and runs, but without that cap (and the compiler path must be set
  or on `PATH`).
- **Local storage only.** No accounts, by design. Two devices do not share progress.
- **The bundled toolchain is large** (~1.2 GB unpacked). You can delete `tools/mingw64` and
  `tools/winlibs.zip` and point `CPP_LAB_GXX` at any other g++ instead.
- **The capstone is single-file in the browser.** Real projects are multi-file; lesson i11
  teaches headers and separate compilation in one file, and the repo shows the layout, but
  the Run button only compiles one `main.cpp`.
- **No autocomplete or linter in the editor.** Deliberate: the compiler is the teacher.
